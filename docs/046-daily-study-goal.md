# 046 1日の目標枚数と未達成リマインダー

**フェーズ:** 将来
**ステータス:** **完了（2026-08-09・実機確認済み）**
**要ネイティブ再ビルド:** 不要（JS のみ）
**依存:** 023/031（通知リマインダー・`notification_schedules`）・039（学習タイマー＝挙動と UI の雛形）
**被依存:** なし

---

## 概要

**1日の目標枚数**を設定できるようにし、それを2つの用途で使う。

1. **達成アラート** — 学習中に今日の枚数が目標に届いたらアラートを出し、学習終了へ遷移できる
2. **未達成リマインダー** — 既存の通知スケジュールに「目標が未達成のときだけ通知する」オプションを足す

```
設定: 1日の目標枚数 = 20枚

学習中  … 今日の累計が20枚に到達 → 「目標達成」アラート →［続ける］/［学習を完了］
20:00   … 今日の累計が20枚未満なら通知（達成していれば通知しない）
```

**目標は1つで、2つの用途が共有する。** 目標を1枚にしておけば未達成リマインダーは
そのまま「学習漏れ通知」になる。

---

## なぜ必要か

039 の学習タイマーは「**時間**で区切りたい人」に応えているが、「**量**で区切りたい人」
（今日はカード20枚だけ）には対応していない。目標枚数はその穴を埋める。

リマインダー側は別の問題を解く。**連続学習が続いているのに、その日たまたま忘れて途切れる**
のが最も惜しい壊れ方で、現状の通知は「指定時刻に無条件で飛ぶ」ため、
**すでに学習し終えた日にも催促が来る**（ノイズ）一方で、**忘れている日を特別扱いできない**。
条件つきにすると、この2つが同時に解消する。

## 確定仕様（設計合意・2026-08-09）

| 論点 | 決定 |
|---|---|
| 目標の単位 | **1日単位**（セッション単位ではない）。リマインダーと同じ目標を共有するため |
| 枚数の定義 | `getTodayReviewedCount(db)` ＝ **その日に学習した実カード枚数**（同じカードを複数回評価しても1枚） |
| 達成時の挙動 | **アラート＋学習終了へ遷移**（039 のタイマー終了と同じ形） |
| 発火条件 | **セッション中に閾値をまたいだときだけ**（開始時点で既に達成済みなら出さない） |
| リマインダーの持ち方 | **既存の通知スケジュールのオプション**（新機能として独立させない） |
| 未達成判定と due | **due が0枚の日でも通知する**（設定にはしない・下記） |
| 目標 OFF のとき | 達成アラートも未達成条件も無効（＝現在の挙動そのまま） |
| Pro ゲート | **なし**（無料機能。学習の継続そのものを支える機能のため） |

### なぜ「1日単位」か

ユーザーの言葉が「**今日は**カード20枚だけ学習」であり、リマインダーも当然1日単位。
セッション単位にすると目標が2つ（セッション用・1日用）必要になり、設定が増える。

**代償**：1日単位なので「すでに達成済みで新しいセッションを始めた瞬間に発火」しうる。
これは**またぎ判定**（下記）で防ぐ。

### なぜ due 0 の日にも通知するのか（設定にしない理由）

目標は「今日これだけ学習する」という**学習量の宣言**で、復習期限の有無とは独立している。
連続学習の維持が動機である以上、**due 0 の日こそ通知の価値が高い**（そこで途切れるため）。

設定にしなかったのは、①「未達成のみ通知」の下にもう一段ぶら下がり設定画面が深くなる
②**後から足すのは DEFS 1エントリで済むのに、一度出した設定は消しにくい**（可逆性が非対称）。
まず常時通知で運用し、うるさければ足す。

ただし**好みではなく客観的に催促が無意味な条件**だけはロジックで抑止する：
**学習できるカードが1枚も無いとき**（非アーカイブのカードが0枚）は通知しない。
ユーザーに打つ手がない状態のため。

## データモデル

### 設定（`store/settings.ts` の DEFS）

```ts
studyGoalEnabled: boolean;   // 既定 false（＝現在の挙動）
studyGoalCount: number;      // 既定 20。1〜999
```

DEFS に2エントリ＋setter 2行。**`lib/settings-keys.ts` への追加を忘れないこと**
（漏れると JSON エクスポート/インポートで復元されない）。

### DB（Phase 2 で追加）

```
notification_schedules に onlyIfGoalUnmet INTEGER NOT NULL DEFAULT 0 を追加
```

**スケジュール単位のフラグ**にする（全体設定にしない）＝「朝は無条件に通知、
夜は未達成のときだけ」という使い分けができるため。既定 0 ＝既存スケジュールの挙動は不変。

`PRAGMA table_info` 確認つき `ALTER TABLE` で追加（043/044/045 と同型）。
`types/index.ts` の `NotificationSchedule` にも追加する。

> **確認済み（2026-08-09）**：`notification_schedules` は **JSON エクスポート/インポートの対象外**
> （`lib/export.ts` は `decks`/`cards`/`tags`/`card_tags`/`reviews`/`review_logs`/`grade_logs` ＋設定のみ）。
> よって本チケットで列を足してもエクスポート側の対応は要らない。ただし裏を返すと
> **通知スケジュールはバックアップから復元されない**（本チケット以前からの仕様）。
> 直すなら別チケット。iCloud 同期は DB ファイルごと往復するので、そちらでは同期される。

## 達成アラートの挙動（Phase 1）

### またぎ判定

```
セッション開始時   : goalMetAtStart = (getTodayReviewedCount() >= goal)
評価を送るたびに   : count = getTodayReviewedCount()
                     if (!goalMetAtStart && !alreadyFired && count >= goal) → アラート
```

- **`goalMetAtStart` が true なら、そのセッションでは一切発火しない**（開始した瞬間に出る問題の対策）
- `alreadyFired`（ref）で1セッション1回に制限する。［続ける］を選んだ後に再発火しない

**枚数は評価のたびに DB から数え直す**。ローカルで +1 する方式は、同じカードを再評価
（`再考` で戻ってきたカード）したときに二重に数えてしまう＝`getTodayReviewedCount` は
実カード枚数なので数え方が食い違う。COUNT 1本なので毎回引いてよい。

### 閲覧モード（032）では動かない

`browse=1` のセッションは `submitGrade` を一切呼ばないので、**判定処理を足さなくても
自動的に発火しない**（学習記録が残らない以上、目標にも数えないのが正しい）。

### タイマー（039）との併用

両方 ON なら**先に条件を満たした方**が発火する。同時に2枚のモーダルが出ないよう、
**発火理由を1つの state で持つ**（`'timer' | 'goal' | null`）。文言は別（`study.goalReached*`）。

### 達成後も学習を続けたとき

［続ける］を選んだ後は、そのセッションでは再発火しない。**目標を超えた分も普通に記録される**
（上限ではなく目安なので、止める必要はない）。

## 未達成リマインダーの実装方式（Phase 2）

### 前提：iOS は発火時に条件を評価できない

ローカル通知は**予約時に内容が確定する**。「20時に枚数を見て0なら鳴らす」は OS の機能として
存在しない。実際、既存の `scheduleFromDb()` も **due 枚数を予約時に本文へ焼き込んでいる**
（発火時の値ではない）。したがって条件つき通知は次の形になる。

```
① onlyIfGoalUnmet のスケジュールは repeats:true を使えない
   （「今日だけスキップ」ができないため）
   → DATE トリガーで N 日分を前倒し予約する
② 目標を達成した瞬間に、その日の分をキャンセルする
   （学習中はアプリが開いているので確実に効く）
③ フォアグラウンド復帰時とセッション終了時に予約を積み直す
```

③ の作法には前例がある：`scheduleFromDb()` は cancel-all → 再登録で、
`syncBreakEndNotification()` が「cancel-all の後に復元する」役を担っている。同じ場所に足す。

### 予約本数の上限（重要）

**iOS の保留ローカル通知は64件が上限**で、超えると古いものから捨てられる。
現在でも「スケジュール5件 × 曜日7」で最大35件を使う設計なので、前倒し分と合わせると
上限に当たりうる。**先読み日数は固定にせず、残り枠から決める**：

```
無条件スケジュールの予約数 = A（既存どおり repeats:true）
条件つきの先読み日数 D = clamp(floor((60 - A) / 条件つきスケジュール数), 1, 7)
   ※ 60 は 64 に対する安全マージン（休憩終了通知 039 などの臨時予約分）
```

D を1日まで縮めても成立する（毎日アプリを開けば毎日積み直される）。

**実測（2026-08-09）**：`MAX_SCHEDULES = 5` の現状では、どう組んでも**最悪36件**（上限64）で
届かない。計算は `lib/studyGoal.ts` の `computeGoalLookaheadDays()` に切り出し、
**最悪ケースを総当たりで検算する assertion を `npm run verify:db`（T17）に入れてある**。
⚠️ **`MAX_SCHEDULES` を増やすとこのテストが落ちる**（10件で71件＝上限超過）ので、そのときに
先読み日数か枠の設計を見直すこと。上限を超えた場合の症状は「設定したはずの通知が一部だけ
黙って来ない」で、エラーが出ないため発覚が遅れる。

### 限界（正直に書いておく）

- **複数端末**：iCloud は DB を同期するが**通知の予約は同期しない**。iPad で目標を達成しても
  iPhone 側の予約は消えないため、iPhone を開かない限り誤通知が飛ぶ。緩和は
  「フォアグラウンド復帰時に再計算」まで
- **先読みの窓**：D 日を超えてアプリを開かないと予約が尽きる。ただしその状態＝学習していない
  なので、通知が来ないこと自体の実害は小さい
- **当日の日付境界**：`todayLocalRange()` に合わせる。端末の時計・タイムゾーン変更時は
  次回フォアグラウンドで積み直される

### 通知文

未達成リマインダーは通常のリマインダーと文言を変える（`notification.goalUnmetBody`）。
**予約時点の残り枚数を焼き込む**と発火時にはズレているので、**枚数を含めない**文言にする
（例：「今日はまだ学習していません」／「今日の目標が残っています」）。

## UI

```

```

### 設定 →「通知」（`app/settings/notifications.tsx`）

各スケジュールの編集にチェックを1つ足す。

```
20:00  平日                          [ ✓ ]
  □ 目標が未達成のときだけ通知する
     ※ 1日の目標枚数を設定していないときは無効
```

**目標が OFF のときはこの行を無効化（またはヒントを出す）**。有効にしても常に未達成
扱いになり毎日鳴る、という分かりにくい状態を避ける。

```

今日の目標 20 枚を学習しました
      ［続ける］  ［学習を完了］
```

#### フォアグラウンド表示（実装後に追加）

未達成リマインダーは**学習セッション中以外ならアプリ起動中でもバナーを出す**
（`lib/notifications.ts` の `setNotificationHandler`・判定用に `setStudySessionActive` を新設）。

当初は既存の通知ハンドラをそのまま引き継いで**常に非表示**だった（休憩終了通知 039 以外は
フォアグラウンドで出さない実装）。しかし**通知は発火した時点でその日ぶんを消費し再送されない**
ため、20時にたまたまアプリを開いていると**その日の唯一のリマインダーが黙って消える**。
「うっかり途切れるのを防ぐ」という機能の目的と噛み合わないので改めた。

デイリーリマインダー（無条件）と挙動が違うのは意図的：あちらは毎日来るので1回消えても翌日また
来るが、**未達成リマインダーはその日限りの条件つき**なので、消えると意味を失う。
一方**学習セッション中だけは抑制する**（学習している最中に「目標が残っています」と出すのは
明確に誤りのため）。判定は `isScreenFocused && !completed`＝タイマーの UI 可視判定と同じ式だが、
**意味が違うのでフラグは別に持つ**（片方の条件を変えたときにもう片方が巻き添えにならないように）。
実機確認済み（2026-08-09・学習中は出ない／他画面では出る）。

通知時刻に**学習セッション中だった**日は、抑制されたまま消費されるのでその日のリマインダーは
失われる（学習終了後にも来ない）。これは**完了画面の目標進捗**（下記）で埋めた。

#### 完了画面の目標進捗（実装後に追加）

学習完了画面に **今日の目標に対する進捗を1行**出す（`app/study/session.tsx`）。

```
✓ 学習完了！
⚑ 今日の目標まで あと 8 枚（12 / 20）      ← 未達成
⚑ 今日の目標 20 枚を達成しました            ← 達成（緑）
```

**達成／未達成の両方を出す**。未達成のときだけ出すと責められている印象になるので、常に情報として置く。
**残り枚数は入れ子 `Text` でサイズ・太さ・色を上げる**（`xl`・太字・青）＝この画面で唯一
「次に何をすればよいか」に直結する数字なので、文章に埋もれさせない。青はホームの件数表示と同じ
（このアプリで数を強調する色）で、達成時の緑と自然に対比する。i18n はラベル／単位／進捗の3つに
分けてあり、日本語「〜あと **8** 枚（12 / 20）」・英語「To today's goal: **8** cards (12 / 20)」の
どちらも語順が崩れない。

これが解いている問題は2つ：

1. **上記の取りこぼし** — 通知時刻に学習中だった日は、その直後に必ずこの画面を見るので届く。
   通知を出し直す案（抑制を記録して数分後に再予約）は、日付境界・二重通知・深夜の抑制といった
   手当てが要るうえ、これまで踏んだ不具合はどれも「通知と状態のズレ」だったため採らなかった。
   **ユーザーが既に見ている場所に置くほうが副作用が無い**
2. **目標がアプリ内のどこにも出ない** — それまで目標は達成アラートと通知でしか姿を見せず、
   「今日は何枚やったか／あと何枚か」を確認する場所が無かった

枚数は達成アラートと同じ `getTodayReviewedCount(db)`（同じカードを何度評価しても1枚）。
閲覧モードでは取得も表示もしない（記録が残らないため）。

#### 一覧のバッジと、目標 OFF との矛盾（実装後に追加）

**一覧に「未達成通知」バッジを出す**（`app/settings/notifications.tsx` の行・時刻の下）。
開かないと分からない設定なので、時刻だけ見て「毎日鳴る」と誤解するのを防ぐ。
`DeckStagesModal` の「既定」バッジと同じ見た目に揃えてある。

これを作る過程で穴が見つかった：**目標を OFF にすると、`onlyIfGoalUnmet` のスケジュールは
1件も予約されない**（`scheduleGoalReminders` が早期 return する）。一覧では有効（✓）のままなので、
**「有効と表示されているのに絶対に鳴らない」という嘘の状態**になる。しかも編集モーダルの
トグルは目標 OFF のとき `disabled` なので、目標を戻さない限り解除もできない。

対応は**目標の ON/OFF 時に2択で決めてもらう**（032 のアーカイブ済みデッキ学習と同じ идиом）：

```
目標を OFF にするとき（有効かつ条件つきのスケジュールがある）
  ※ 選択されるまで目標の設定を適用しない（トグルは ON のまま）
  「…が N 件あります。目標をオフにすると…これらは鳴らなくなります。どうしますか？」
    [これらの通知をオフにする]   … 目標 OFF ＋ enabled=false（**条件の指定は残す**＝目標を戻せば復元できる）
    [通常の通知として鳴らす]     … 目標 OFF ＋ onlyIfGoalUnmet=false（**普通のスケジュールに変える**）
    余白タップ / Esc            … **完全なキャンセル（目標は ON のまま）**

目標を ON にするとき（無効かつ条件つきのスケジュールがある）
  ※ ON は矛盾を生まないので先に適用してよい（あとに出すのは任意のお誘い）
  「…が N 件オフになっています。オンに戻しますか？」
    [オンに戻す] [そのままにする] / 余白タップ … いずれも整合した状態
```

**OFF だけ「選ぶまで適用しない」のは非対称に見えるが意図的**：OFF は矛盾（一覧では有効なのに
絶対に鳴らない）を生むので**全ての出口が整合した状態に着地する必要がある**。閉じたときに
設定だけ適用済みだと、**そのダイアログが防ごうとしている状態そのものに着地してしまう**。
一方 ON はそれ自体では何も壊さないので、閉じても「目標 ON・それらは OFF」で整合している。
ここを揃えて ON 側にも確認を挟むと、無害な操作に確認を出すことになり煩わしいだけ。
なお「閉じる＝キャンセル」は削除確認・破棄確認・032 のアーカイブ済みデッキ学習と同じ流儀。

**検討して不採用にした案**：

- **目標 OFF のとき条件を無視して通常どおり通知する（実行時フォールバック）** —
  沈黙は防げるが、**ユーザーがまさに避けたかった「毎日鳴る」を復活させる**。
  「未達成のときだけ」を選んだ人は「やった日は鳴らさないでほしい」と言っている
- **自動でトグルを書き換える（確認なし）** — 身に覚えのない設定変更が起きる。
  特に ON 方向は、ユーザーが自分の意思でオフにしたスケジュールを勝手に復活させてしまう
  （「なぜオフか」を区別するには DB 列が要るので、確認1回で済ませる方が軽い）
- **目標 OFF で `onlyIfGoalUnmet` を一律 false に落とす** — 目標を戻したときに設定が失われている

なお**バッジは目標 OFF のとき注意色で「未達成通知（目標オフ）」を出す**ようにしてある。
上の対応でこの状態は起きなくなるが、**iCloud 同期で他端末から入ってくる**可能性があるため
保険として残す（DB は同期されるが、この2択ダイアログは操作した端末でしか出ないため）。

#### 実装メモ

- **条件判定の実体は「達成した瞬間のキャンセル」**。iOS は発火時に条件を評価できないので、
  予約は「未達成である前提」で置いておき、達成した時点で当日分を消す。学習中はアプリが
  開いているのでこのキャンセルは確実に効く
- **当日分だけ消して明日以降は残す**：今日の達成は明日の催促を止める理由にならない
- **`scheduleFromDb` は cancel-all → 再登録**なので、条件つき通知も毎回作り直される。
  そのため「予約が尽きる」対策の補充と「達成状況の反映」が同じ経路で片付く
  （⚠️ 039 の休憩終了通知も巻き込んで消えるため、既存の `syncBreakEndNotification()` による
  復元がそのまま必要＝呼び出し順は変えていない）

## 不採用（再提案しないこと）

- **バックグラウンド処理で発火時に条件判定する**（`expo-background-task` 等）
  — iOS は実行タイミングを保証しないため「20時ちょうどに判定」が成立しない。
  予約＋達成時キャンセルの方が確実
- **目標をセッション単位にする** — リマインダーと目標を共有できず設定が2つに増える。
  「今日は20枚」という自然な言い方とも合わない
- **due 0 の日は通知しない設定を設ける** — 目標は学習量の宣言で due とは独立。
  連続学習の維持が動機なので due 0 の日こそ通知の価値が高い。
  設定は後から足せる（DEFS 1エントリ）ので、まず常時通知で運用する
- **目標達成時に学習を強制終了する** — 目標は上限ではなく目安。［続ける］を必ず用意する
- **未達成通知に残り枚数を書く**（「あと5枚です」）— 予約時点の値しか書けず、
  発火時にはズレている。枚数を含めない文言にする
