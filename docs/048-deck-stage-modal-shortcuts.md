# 048 デッキ土台モーダルのキーボードショートカット

**フェーズ:** Phase 1 実装 / Phase 2 保留
**ステータス:** Phase 1 = 実装済み ／ **Phase 2 = 未着手（必要と感じてから着手する）**
**要ネイティブ再ビルド:** 不要（JS のみ）
**依存:** 034（ネイティブ UIKeyCommand）・044/045（土台の複数持ち）・043（HTML 画像ライブラリ）
**被依存:** なし

---

## 概要

デッキ編集／新規作成から開く2つのシートに、ハードウェアキーボードのショートカットを足す。

- **土台一覧**（`DeckStagesModal`・HTML/CSS 土台と SQL 初期化で共用）
- **土台の編集面**（`SqlInitModal`）

現状この2つは **Esc（閉じる）しか受けていない**。土台の追加・編集・削除がすべてタップ専用で、
外付けキーボードでデッキを組み立てているときにここだけ手がキーボードから離れる。

---

## Phase 1（実装する範囲）

### 土台一覧（`DeckStagesModal`）

| キー | 動作 |
|---|---|
| `J` / `K` | 土台のフォーカス移動（ヌルサイクル＝末尾の次はフォーカスなし） |
| `Return` | フォーカス中の土台を開く（編集面へ） |
| `Delete`(Backspace) | フォーカス中の土台を削除（既存の削除確認モーダルを経由） |
| `N` | 土台を新規追加（＝ヘッダーの ＋。追加後はそのまま編集面が開く） |
| `Esc` | 階層ディスマス：削除確認 → 編集面 → **フォーカス解除** → 一覧を閉じる |

### 土台の編集面（`SqlInitModal`）

**キーは足さない（実装中に判断を変更）。**`Esc` = 閉じる のみ、従来どおり。

当初は `N`（名前欄）・`C`（コピー）を足す予定だったが、実装時に**この面ではほぼ発火しない**ことが
分かった。この面は `autoFocus` で開くため常に本文の入力欄にカーソルがあり、文字キーは入力欄に
消費される（034 の住み分け）。カーソルを外す手段は「シート内のどこかをタップ」しかない
（`Esc` は閉じる）。つまり N/C を使うには先にタップが要るが、その時点で名前欄もコピーボタンも
同じだけタップで届く。**キーを増やしても操作は速くならない**ので入れない。

---

## 設計判断

### 「保存（S）」は割り当てない

**この2つのシートに保存は無い。**`DeckStagesModal` の ✓ も `SqlInitModal` の ✓ も `onClose` を
呼ぶだけで、入力はライブで親 state に反映され、実際の保存はデッキ編集画面の保存ボタンが行う。
つまり `S`（保存）は `Esc`（閉じる）と同じ動作になり、キーを増やす意味がない。
「シートを閉じてデッキも保存する」は別の新しい挙動で、誤爆すると意図せずデッキが保存されるため
今回は入れない。

### 編集面の名前欄は `T` ではなく `N`

デッキ新規作成・編集で **`N` ＝ 名前欄**という規約が既にある。同じ「名前」に別のキーを当てると
覚え直しになるため揃える。

### 編集面の `Esc` は「即閉じる」のまま変えない

「1回目でカーソル解除、2回目で閉じる」に変える案は**不採用**。この面は `autoFocus` で開いた瞬間から
カーソルが入っているので、**閉じるのに必ず2回押す**ことになりキーボード操作が後退する。
現在の「Esc は即閉じる（確定＝ライブ値を保持）」は 044 時点の意図的な設計でもある。

### 矢印キーは使わない

デッキ新規作成・編集と同じ方針（文字キー＋住み分けで完結）。iPad の UIFocusSystem が
修飾なし矢印を横取りする問題（CLAUDE.md の iPad の落とし穴）に踏み込まないため。

## Phase 2（保留：画像ライブラリのキー操作）

**着手しない。** 必要と感じたときに、この節を出発点にする。

### やるとしたら

`J`/`K` を**土台 → 画像と通しでサイクル**させる（新しいキーを増やさない）。
フォーカスが画像に入ったらライブラリを自動展開する。`Return`=リネーム、`Delete`=削除、
`C`=タグをコピー。

前例は**学習画面のコードブロックの通しサイクル**（裏面のブロック → メモのブロックを通しで送り、
メモに到達すると自動展開する）。同じ形なので、移動の考え方を新しく覚える必要がない。

### ⚠️ 検討して**不採用**にした案（再提案しない）

`I` で画像エリアへ入り、繰り返し `I` で画像を送り、`S` で土台へ戻る方式。

- **難しさが減らない**：重いのは後述の4点で、この案はどれも減らさない。減るのは
  「境界をまたぐ計算」だけで、そこは元々 20 行程度の安い部分（前例もある）
- **キーの語彙が増える**：移動手段が2種類（エリア内は J/K、エリア間は I/S）になる
- **`I` の役割が変則的**：「入る」と「送る」を同じキーが担うと、画像側にいるとき J/K が
  何をするのか（重複するか、効かない例外を作るか）という問いが残る
- **`S` は既に他の意味**：入力系モーダルでは保存、一覧では選択モード開始。3つ目の意味になる。
  `I` も親のデッキ編集画面ではアイコン選択

### Phase 2 の実装コストが集中する4点（どの移動方式でも等しく必要）

1. 画像の行にフォーカス枠を描く（`HtmlImageLibrary` にフォーカス状態を渡す）
2. **入れ子スクロール**の両方で自動スクロールする（外側のシート＋高さ上限つきの画像リスト）
3. **折りたたまれているときの扱い**（フォーカスが入ったら展開する＝押しただけでレイアウトが動く）
4. **コンポーネント境界**を越えて操作を届ける。`HtmlImageLibrary` はリネームの下書き・削除確認・
   展開状態を自前で持っており、state を親へ持ち上げるか ref で命令的 API を生やす必要がある

### 保留の理由

画像の追加・リネームは「デッキを作るときに数回」の操作で、キーボードで速くする価値が土台ほど
高くない可能性がある。Phase 1 を使ってみて、それでも画像側が欲しいかを判断する。
