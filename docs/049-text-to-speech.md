# 049 カード本文の読み上げ（TTS）

**フェーズ:** 将来
**ステータス:** **Phase 1a / 1b / 1c = 実装済み（2026-08-18・実機確認待ち）** ／ Phase 2（自動読み上げ）は未着手
**要ネイティブ再ビルド:** **必要**（`expo-speech` はネイティブモジュール。034 の `react-native-key-command` と同じ扱い）
**依存:** なし（034 のキー割当規約には従う）
**被依存:** なし

---

## 概要

カード本文を端末の音声合成（iOS = `AVSpeechSynthesizer`）で読み上げる。

```
学習画面 → 表示中の面（表 / 裏 / メモ）の テキストブロック を読み上げる
         → コードブロックは読まない（読んでも無意味）
```

`expo-speech` を使う。**オフライン・無料・API キー不要**（端末内蔵の音声合成）。
ランニングコストはゼロで、ネットワーク実行（Wandbox・Pyodide）のような外部依存も無い。

---

## なぜ必要か（このアプリでの使い道）

多くの暗記アプリ（Anki・Quizlet）が読み上げを持つのは、**主要ユーザーが語学学習者**だからで、
その価値は「発音を聞く」ことに集中している。**コード暗記ではその価値がほぼ丸ごと消える**
（`const` も `=>` も読み上げる意味がない）。したがって「他のアプリにあるから」は
このアプリでは導入理由にならない。

そのうえで、**このアプリの文脈でも成立する使い道が3つ**ある。これが導入根拠。

1. **英語の技術用語の発音** — `idempotent`・`asynchronous`・`nullish coalescing`・`tuple` は
   日本人開発者が読み方を知らないまま覚えている典型。**「コード暗記アプリだからこそ」の需要**で、
   3つの中で最も説得力がある
2. **ながら学習** — テキストブロック中心の用語Q&A・概念説明なら画面を見ずに聞ける
3. **アクセシビリティ** — VoiceOver とは別に、任意再生ボタンがある意味はある

**1 が本命**である点は以下の設計判断すべてに効いてくる（混在テキストの扱いが最重要になる理由）。

## 混在テキストの扱い（このチケットの核心）

### 仕組み

`Speech.speak(text, { language })` は iOS の `AVSpeechUtterance` に**1つの声**を割り当てる。
**1回の発話＝1つの声**であり、**文中で言語を自動判別して声を切り替える機能は無い**。

### ケース別

| カードの中身 | 指定言語 | 結果 |
|---|---|---|
| 日本語のみ | `ja-JP` | ◎ 問題なし |
| 英語のみ | `en-US` | ◎ 問題なし |
| 日本語のみ | `en-US`（設定ミス） | ✗ ほぼ読めない |
| **日英混在** | `ja-JP` | △ 日本語の声が英語をカタカナ寄りに読む。意味は取れるが**英語の発音としては正しくない** |
| **日英混在** | `en-US` | ✗ 英語の声が日本語を読めない |

### なぜこれが核心か

このアプリのカードは「**日本語の説明文に英語の技術用語が埋まっている**」形が主流になる。
つまり**混在は例外ケースではなく本命ケース**。そして混在で `ja-JP` を選ぶと、
上の「使い道1（英語技術用語の発音）」が成立しなくなる（`idempotent` が "イデンポテント" になる）。

### 解決手段は1つだけ

**アプリ側で文字種ごとに分割し、声を変えて順番に読ませる**（`Speech.speak()` は連続で呼ぶと
キューに積まれて順番に再生される）。判定は Unicode の文字種（かな・漢字 vs ラテン文字）で機械的にできる。

```
「React の useEffect は副作用を扱う」
  → ["React", en] ["の", ja] ["useEffect", en] ["は副作用を扱う", ja]
```

### 分割＝自動判別そのもの（重要な帰結）

分割は1文字ずつ文字種を見るので、**純日本語の文は区間が1つ（ja）・純英語の文も区間が1つ（en）**になる。
つまり **分割を入れると「このカード（デッキ）は何語か」という設定が要らなくなる**。

→ **1c を採ると、日英に関しては Phase 2（デッキ単位）も Phase 3（カード単位）も不要になる可能性がある。**
設定項目が増えないのはこのアプリにとって明確な利点で、**1c の価値は当初の見積もりより高い**。

⚠️ ただし**短いラテン片の日本語寄せは「日本語が混ざっている文」にだけ適用すること**。
無条件に適用すると、表面が `GET` だけの単語カード（ラテン文字しか無い）が「ゲット」と読まれる。
実装済みのプロトタイプはこの条件つき（`hasJa` ガード）。

**副作用（分割を入れる場合に受け入れるもの）**：

1. **切り替えのたびに間が空き、声色が変わる** — 短い単語が頻繁に混ざる文（「OK です」「PC の設定」）は
   途切れ途切れに聞こえる。**構造的に避けられない**
2. **日本語として定着した略語まで英語で読まれる** — 「API を叩く」の `API` が "エイピーアイ" ではなく
   "ay-pee-eye" になる。狙いどおりとも耳障りとも言える
3. **数字と記号の帰属が曖昧** — `3` は日本語側か英語側か。前後の文字に寄せるルールが要る

1 の緩和策として「**短いラテン文字片（2〜3文字以下）は日本語側に含める**」閾値を入れる案があるが、
その閾値自体がチューニング項目になる。**実測してから決める**（＝ Phase 1a の存在理由）。

## 多言語への拡張（2026-08-18 の検討）

### 読み上げ言語とアプリ UI 言語は別物

**混同しないこと。** アプリ UI 言語（`locales/*.json`・047 のチケット）は ja/en のみだが、
**読み上げ言語は iOS に音声が入っている言語すべて**（数十言語）が最初から使える。
`Speech.speak(text, { language: 'es-ES' })` と BCP-47 コードを渡すだけ。

**言語を増やすコストはほぼゼロ。** 選択肢の一覧は `Speech.getAvailableVoicesAsync()` が
端末から返すので、**ピッカーは自動生成できる**（対応表をコードに持たない＝メンテもゼロ）。

### 分割が分けられるのは「文字体系」であって「言語」ではない

これが多言語化の唯一かつ決定的な制約。`Hola` と `Hello` は**どちらもラテン文字**で、
文字コードからは区別できない。

| 組み合わせ | 自動分割 | 理由 |
|---|---|---|
| 日本語 + 英語 | ○ | かな漢字 vs ラテン文字 |
| **日本語 + スペイン語 / フランス語** | **○** | 同上（ラテン側をどの言語で読むか選ぶだけ） |
| 日本語 + 韓国語 | △ | ハングルは独立した文字体系だが**現状は判定していない**（下記＝`ja` 側に落ちる） |
| 日本語 + 中国語 | △ | **漢字と汉字は同じコードポイント**（Unicode の統合漢字）。かなが無い文は判別不能 |
| **英語 + スペイン語** | **✗** | **同じラテン文字。原理的に不可能** |

### 「ラテン文字」の範囲＝U+00C0–U+024F ＋ U+1E00–U+1EFF（2026-08-19 拡張）

当初の `RE_LATIN` は `A-Za-zÀ-ÖØ-öø-ſ`（＝U+017F まで）だったため、**ベトナム語の
`ơ ư`（拡張B）と声調つきの `ạ ế ộ ứ`（拡張追加）、ルーマニア語のコンマ下 `ș ț`** が
漏れていた。漏れた文字は「中立」に落ちて直前の区間へ吸われるので**読み上げの内容は正しい**が、

1. 文の**先頭**に来ると `ja` 区間として始まる（`Ứng dụng` が日本語の声で読まれる）
2. その `ja` 区間のせいで `hasJa` が立ち、**短ラテン寄せが誤爆**して `ứng` のような
   短い語が丸ごと日本語側へ倒れる

の2つが起きていた。**拡張B・拡張追加まで含めて解決**（`LATIN_CHARS` が2つの正規表現の定義元）。
拼音の `ǎ ǐ ǒ ǔ` も拡張Bなので、ついでにラテン側で読まれるようになった。

### 非ラテン側の言語設定（2026-08-19・上の ✗ を解消）

修正前は `JA_LANG = 'ja-JP'` 固定だったため、こうなっていた：

| 文字体系 | 修正前の挙動 |
|---|---|
| **中国語（簡体・繁体）** | 漢字が `RE_JA` に当たるので **`ja-JP` の声で日本語読み** |
| **韓国語・キリル・ギリシャ・アラビア・ヘブライ・タイ・デーヴァナーガリー…** | どちらにも当たらず「中立」→ 先頭が中立なので `ja` 区間 → **`ja-JP` の声**に丸投げ |

**エラーも出ず声も出るのに読みだけが違う**（中国語）／**実質読めない**（その他）という、
一番気づきにくい壊れ方で、しかも固定値なので**ユーザー側に回避手段が無かった**。直したのは3点：

1. **`RE_JA` → `RE_NON_LATIN`**：かな漢字だけでなくハングル・キリル・タイ文字なども
   **能動的に判定する**。中立のままだと「直前の区間へ吸われる」ので、`hello 안녕` の韓国語が
   **英語の声で読まれて**いた（文頭に来たときだけ非ラテン扱いになる**位置依存**の挙動）
2. **`SpeakOptions.nonLatinLang`**：非ラテン区間の言語を設定から受け取る（`speechNonLatinLang`）。
   既定は**端末の言語**（`nonLatinLangForLocale`＝`languageCode`＋`regionCode` を繋ぐだけ・
   対応表は持たない）で、ラテン文字の言語の端末は `ja-JP`＝**従来と同じ**なので既存利用者は不変
3. **短ラテン寄せは非ラテン側が日本語のときだけ**：閾値3は「日本語の声なら `API` を
   『エーピーアイ』と読む」という実測から決めた値で、他言語の声が同じとは限らない。
   日本語以外ではラテン片をラテン側（既定：英語）に残す

⚠️ **`LATIN_CHARS` と `RE_NON_LATIN` は交わらせない**（範囲を重ねて「ラテン判定が先だから
大丈夫」にしない）。短ラテン寄せのガードは**テキスト全体に対する `test`** で文字単位の
優先順位が効かないため、重ねるとベトナム語の `ứng` が「非ラテン文字を含む」と判定されて
日本語側へ倒れる（実際に踏んだ）。U+1D00–U+1EFF を避けて 1CFF で止め 1F00 から再開している。

⚠️ **ガードは区間ではなく元テキストの文字で数える**。区間で数えると、先頭の数字・記号が作る
中立の非ラテン区間を拾ってしまい、`1. GET` のような英語カードで `GET` が「ゲット」になる
（`hasJa` 時代からあったバグ。同時に修正）。

**残る制約**：非ラテン側も**1つの声**なので、日本語と韓国語が同居するカードは分けられない。
→ **`docs/050` で解消する**（文字体系ごとの解決表にする。ハングル・タイ・キリルなどは
1対1で決まるので設定不要で読み分かる。⚠️ 本ドキュメントの「設定は1つになる」という結論は
**日本語⇔韓国語などにまで一般化してはいけない**＝分けられないのは同じ文字を共有する言語同士だけ）。

### したがって設定は「どちらの文字体系を何語として読むか」2つになる（→ 050 で一般化）

⚠️ **この節は 050 に置き換わっている**。「2つ」は非ラテンを1バケツに畳んでいた前提の話で、
現在は**文字体系ごとの解決表**（`speechScriptLangs`）になり、ハングル・タイ・キリルなどは
設定なしで読み分ける。以下は当時の判断の記録として残す。

```
ラテン文字の区間     → 設定で選んだ言語の声（既定：英語）
ラテン文字以外の区間 → 設定で選んだ言語の声（既定：端末の言語。日本語端末なら日本語）
```

「デッキの言語」ではなく「**この文字体系が出てきたら何語として読むか**」という意味づけになる。
日本語話者がスペイン語を学ぶデッキならラテン側を es-ES にするだけで日西混在カードが正しく読まれ、
韓国語話者は非ラテン側を ko-KR にするだけで韓国語カードが読まれる（**分割のコードは変えない**）。

⚠️ 当初は**非ラテン側を `ja-JP` 固定**にしていた（2026-08-19 に設定化）。固定だと中国語・韓国語・
ロシア語などのカードが**日本語の声に丸投げされ、ユーザー側に回避手段が無かった**。下記参照。

### 自動言語判定（統計的な判定ライブラリ）は採らない

英語とスペイン語を自動で言い分けるには n-gram ベースの言語判定が必要になるが、
**カードは短文なので精度が出ず、挙動が予測不能になる**（同じデッキでカードごとに読み方が変わる）。
バンドルサイズも増える。**採らない。再提案しない。**

### 唯一の現実的な破綻ケース（許容する）

**スペイン語話者が「スペイン語の説明文＋英語の技術用語」のカードを作る場合**は英西混在なので
分けられない（`useEffect` がスペイン語読みになるか、説明文が英語読みになるかの二択）。

ただしこれは**分割を入れなかった場合に日本語話者が直面する妥協とまったく同じもの**であり、
分割を入れることで日本語話者は救われ、スペイン語話者は現状維持になる＝**誰も悪化しない**。
1枚のカードに英語とスペイン語が同時に混ざる場面は稀なので、この破綻は許容する。

## 実測から分かったこと（実装に効く3点）

### 1. 閾値が「3文字以下」である理由 ＝ 英語の声は略語を単語として読む

**2文字以下**にすると `API`（3文字）が英語側に残り、**英語の声が「アピ」と単語のように読んでしまう**
（TTS は辞書に無い略語を綴り読みではなく単語として発音することがある）。
**3文字以下**にすれば `API` は日本語側へ倒れ、日本語の声が「エーピーアイ」と正しく読む。

⚠️ **残る確認事項**：この理屈だと **4文字以上の略語（`HTML`・`JSON`・`HTTP`）は英語側に残る**。
`JSON` は英語読み（ジェイソン）が正しいので問題ないが、`HTML` のような綴り読みすべき語が
単語として読まれないかは 1b の実装後に実カードで確認する。閾値をこれ以上上げると
`useEffect` のような本来英語で読ませたい語まで倒れるので、**閾値の引き上げでは解決しない**
（必要なら例外辞書だが、まずは実カードで問題が出るか確認してから）。

### 2. 英語の声は日本語を「無音でスキップ」する（④）

崩れて読むのではなく**丸ごと飛ぶ**。これは CLAUDE.md の
「オンに見えるのに効いていない状態を作らない」に該当する最悪の壊れ方で、
**「全部英語で読む」という選択肢をユーザーに露出させてはいけない**根拠になる。
分割を入れる以上この状態は発生しないが、将来 UI に言語の直接指定を足すときは思い出すこと。

### 3. サイレントスイッチは問題にならなかった

`useApplicationAudioSession` の true/false どちらでも音が出た。
**設定項目にはしない**（既定のまま）。前提として挙げていた「サイレントスイッチで無音になる」
落とし穴は**実測では再現せず**、設定画面の注記も不要と判断する。

## 設計判断

### カード単位の「表/裏それぞれの言語設定」を先に入れない

他アプリにある方式だが、このアプリでは**先に入れない**。理由は3つ。

1. **混在問題を解決しない（決定的）** — あの方式が効くのは「表＝英単語／裏＝日本語訳」のように
   **面ごとに言語が綺麗に分かれている**語学カードだけ。1つの面の中に日英が混ざるこのアプリでは、
   面ごとに設定できても「その面をどちらの声で読むか」を選ぶだけで結局どちらかが犠牲になる。
   **カード単位の言語設定と文字種分割は別の問題**であり、効くのは後者
2. **運用されない** — 数百枚のカードに1枚ずつ言語を設定する操作は現実に行われない
3. **波及が大きい** — 下記の6点セットが必要

カード単位を入れる場合に触る箇所（Phase 3 に着手するときの作業リスト）：

- `cards` に `frontLang` / `backLang` を `ALTER TABLE` で追加
- `types/index.ts` の `Card`、`lib/database/cards.ts` の `toCard`/`create`/`update`/`duplicateCard`
- `BlockEditor` の表/裏タブに言語ピッカー2つ（**UI が最も増える箇所**）
- **`lib/export.ts` は cards を `SELECT *` ではなく列指定している**（`export.ts:101`）。
  足し忘れるとエクスポートから静かに落ちる。`lib/import.ts` も同様
- `lib/tsv.ts` は往復しないので `inspectTsvExport` の警告項目に追加（044/045 と同じ扱い）
- `scripts/verify-db.ts` にマイグレーション検証を追加

### デッキ単位（Phase 2）は DB マイグレーション不要

**`decks.language` 列がすでに存在していて完全に未使用**（`app/deck/new.tsx:98` で `'ja'` 固定・
編集 UI なし・読む場所なし）。これをデッキの読み上げ言語として使えば `ALTER TABLE` が要らない。
`decks` は `lib/export.ts` で `SELECT *` されているので **JSON 往復も自動で通る**。

⚠️ ただし**既存デッキはすべて `'ja'`** になっている（既定値のまま書き込まれてきたため）。
「デッキ既定＝アプリ設定に従う」を表す値（`''` か `'system'`）を別に用意しないと、
**全既存デッキが日本語固定として扱われる**。Phase 2 に着手するときは既定値の扱いを先に決めること。

### Pro ゲートにしない

iOS 標準 TTS は無料・無制限で、外部 API のようなコストが発生しない。
機能の原資が無いところに課金ゲートを置くと「なぜ有料か」を説明できない。
Pro にするなら「自動読み上げ」だけが候補。

### 読み上げボタンは**ヘッダーではなく左下のフローティング**

当初はヘッダー右に置いたが、**編集・完了と合わせて3個並び、長いデッキ名とタイトルが重なった**
（iPhone で実機報告）。原因はタイトルの中央寄せ箱が**両側 56pt しか確保していなかった**こと
（1個ぶんの値のまま）。ボタン1個 36pt なので3個には 116pt 要る。

対処は2つ。①**読み上げをヘッダーから外して左下の FAB にする** ②タイトルの確保幅を
**56 → 80pt**（＝実際の 8 + 36×2）に直し、今後ボタンを増減しても重ならないようにする。

左下を選んだ理由：

- **カード本文は左上から始まる**ので、左上に置くと必ず1行目に重なる。左下は
  内容が縦中央寄せ（`justifyContent: 'center'`）なので**短いカードでは空いている**
- **親指で届く**（学習中に押す機能として、ヘッダーより適切）
- **カードの外側に兄弟として重ねるので反転抑止（`FlipSuppressContext`）が要らない**
  ＝タップはカードに届かない（学習タイマーと同じ方式）
- 下段（表面＝前後送り列／裏面＝評価ボタン列）の**高さは表裏で違う**ので、
  `onLayout` で実測して真上に置く（固定値だとズレる）

⚠️ **`zIndex` は休憩オーバーレイ（15）より下（10）にする**。読み上げはカード操作なので、
休憩中（039）はグレーアウトに覆われて押せないのが正しい。タイマー（20）だけが休憩中も操作できる。

### 配色は「丸はカード色のまま・アイコンは青の塗りつぶし」

当初は真下の ◀ と同じ配色（カード色＋枠＋**グレー**アイコン）にしたが、
**同じ見た目の丸が縦に2つ並ぶだけで役割の重要度が違う**ため見分けがつかなかった。

| 状態 | 見た目 |
|---|---|
| 待機 | カード色の丸＋枠＋**青**の `volume-high`（塗りつぶし） |
| 再生中 | **薄い青**の丸（`primary + '20'`）＋枠＋**青**の `stop`（塗りつぶし） |

- **アイコンを青にする**ことで ◀（グレー）と役割が違うことを待機中から示す
- 輪郭線ではなく**塗りつぶし**にして、小さいサイズでも形が読み取れるようにする
- 再生中は**薄い青の下地**を敷く。アイコンの形（スピーカー ⇄ 停止）だけでは
  鳴っているかが分かりにくいため。`+ '20'` はデッキアイコン（`lib/deckIconColors.ts`）・
  `IconPickerModal` と同じアルファ付与の慣習

⚠️ **青ベタにはしない**（待機中も再生中も）。このアプリの FAB には
「主操作＝青ベタ＋白アイコン」「控えめ＝カード色＋枠」の2つの型があり、
読み上げは**補助機能**なのでカード本文や裏面の評価ボタンより目立つのは重要度の順序が狂う。
再生中だけ青ベタにする案は、状態変化のために型をまたぐと主操作に見えるため不採用にし、
**薄い下地**で「控えめの型」に留まったまま状態を示す形にした。

### 長いカードで最後の行が FAB に隠れないようにする

`contentContainerStyle` の `paddingBottom` **ではなく `contentInset` を使う**。
`faceContent` は `flexGrow:1 + justifyContent:'center'` なので、padding を足すと
**短いカードで内容が上へずれる**（中央寄せの箱が縮むため）。`contentInset` はレイアウトを
変えずスクロール可能範囲だけを伸ばすので、狙った効果だけが出る。
`bounces={false}` でもインセット分は正当なスクロール範囲なので届く。

### 止め忘れは「経路ごとに `stop()`」ではなく「表示が変わったら止める」で防ぐ

カード送り・表裏反転・メモ開閉・画面離脱の**各経路に `stop()` を書くと必ずどれか漏れる**
（前のカードの読み上げが次のカードに被る）。そこで
`useEffect(() => stop(), [currentCard?.id, isFlipped, showMemo])` ＝
**「いま読んでいる対象を決める値」が変わったら止める**、という1箇所に集約した。
画面離脱（カード編集モーダルへの push を含む）は `useFocusEffect` のクリーンアップが担当する。
