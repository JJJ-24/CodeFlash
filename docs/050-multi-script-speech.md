# 050 読み上げの多言語対応（文字体系 → 言語の解決表）

**フェーズ:** 将来
**ステータス:** **Phase 1 = 完了（2026-08-20・実機確認済み）** ／ Phase 2（デッキ単位）は未着手
**要ネイティブ再ビルド:** 不要（`expo-speech`・`expo-localization` とも導入済み）
**依存:** 049（読み上げ本体）
**被依存:** なし

---

## 概要

読み上げの言語決定を「ラテン文字／それ以外」の**2バケツ**から、**文字体系ごとの解決表**へ広げる。

```
現在（049）  ラテン文字 → 設定の言語 ／ それ以外 → 設定の言語（1つ）
本チケット   ラテン文字 → 設定 ／ かな → 日本語 ／ ハングル → 韓国語 ／ タイ文字 → タイ語 …
             漢字 → 設定（日本語 or 中国語）／ キリル → 設定（既定ロシア語）…
```

狙いは **日本語と韓国語・中国語・ロシア語などが混ざるカードを、設定なしで読み分けること**。
語学学習で使うと現状は「日本語と英語」しか読み分けられず、韓国語カードも日本語の声で読まれる。

---

## なぜできるのか（前提の訂正）

049 では「分けられるのは文字体系であって言語ではない」と書き、そこから
「**設定は1つ**（ラテン文字を何語で読むか）」を導いた。この推論は**片側が誤り**だった。

文字体系で分けられないのは「**同じ文字を共有する言語同士**」だけで、
**日本語と韓国語・タイ語・ロシア語・ギリシャ語などは文字体系そのものが違う＝原理的に分けられる**。

| 組み合わせ | 自動判別 | 理由 |
|---|---|---|
| 日本語 ⇔ 韓国語 | **○** | ハングルは韓国語しか使わない |
| 日本語 ⇔ ロシア語 / タイ語 / ギリシャ語 / アラビア語 / ヒンディー語 | **○** | いずれも固有の文字体系 |
| 日本語 ⇔ 英語・スペイン語… | **○** | かな漢字 vs ラテン文字（049 で実装済み） |
| **日本語 ⇔ 中国語** | **△** | 漢字は同じコードポイント。**かなの有無**で推定はできる |
| 英語 ⇔ スペイン語 ⇔ ベトナム語 | **✗** | 同じラテン文字。**原理的に不可能** |

つまり ✗ は2つだけ（ラテン文字の中／漢字の中）で、そこにだけ設定を置けばよい。
049 が日韓を分けられないのは Unicode の制約ではなく、**非ラテンを1バケツに畳んだ実装の都合**。

## 確定仕様（設計合意・2026-08-20）

| 論点 | 決定 |
|---|---|
| 解決の単位 | **文字体系**（`SpeechScript`）→ 言語（BCP-47） |
| 設定を置く範囲 | **曖昧な文字体系だけ**（ラテン・漢字・キリル・アラビア・デーヴァナーガリー）。1対1のものは設定を出さない |
| 既定値 | 1対1の文字体系はその言語。曖昧なものは端末言語から（日本語端末なら漢字＝日本語） |
| 粒度 | Phase 1 = アプリ設定 → Phase 2 = **デッキ単位の上書き** → カード/面単位は**やらない**（下記） |
| 漢字の曖昧さ | **かな/ハングルが同じ面にあれば日本語/韓国語**、無ければ設定値（推定であって確定ではない） |
| 発話の分割 | **細かく割ってから、同じ言語に解決された隣接区間を畳む**（下記） |
| Pro ゲート | なし（049 と同じく無料機能） |

## 設計

### 1. 細かく割ってから、言語で畳む

素直に文字体系で割ると**日本語の文が漢字とかなで細切れになり**、発話境界だらけで間延びする
（`Speech.speak()` は1発話ごとに間が入る）。順序を分けることで解決する。

```
splitByScript(text)        文字体系で細かく割る（kana / han / latin / hangul …）
  ↓
resolveLangs(runs, langs)  各区間を言語へ解決する（han の推定はここ）
  ↓
mergeByLang(runs)          隣り合う同じ言語の区間を畳む  ← 日本語は漢字＋かなで1発話に戻る
  ↓
speakText                  区間ごとに声を変えてキューへ積む
```

⚠️ **畳むのは「文字体系が同じ」ではなく「解決後の言語が同じ」区間**。ここを間違えると
日本語が細切れのままになるか、漢字＝中国語の設定時に日本語と中国語が1発話に混ざる。

### 2. 文字体系の一覧（範囲表）

`lib/speech.ts` に `SCRIPT_RANGES` を持つ。現在の `RE_NON_LATIN` を分解して名前を付けるだけ。

| script | 主な範囲 | 既定の言語 | 設定 |
|---|---|---|---|
| `latin` | 現在の `LATIN_CHARS`（ASCII＋U+00C0–U+024F＋U+1E00–U+1EFF） | `en-US` | **あり**（既存） |
| `kana` | U+3040–U+30FF・U+31F0–U+31FF・**U+FF66–U+FF9F（半角カナのみ）** | `ja-JP` | なし |
| `han` | U+3400–U+4DBF・U+4E00–U+9FFF・U+F900–U+FAFF | 端末言語（`zh`/`ko` なら該当、他は `ja-JP`） | **あり** |
| `hangul` | U+1100–U+11FF・U+3130–U+318F・U+A960–U+A97F・U+AC00–U+D7FF・U+FFA0–U+FFDC | `ko-KR` | なし |
| `cyrillic` | U+0400–U+052F・U+1C80–U+1C8F | `ru-RU` | **あり**（uk/bg/sr/mk/be） |
| `greek` | U+0370–U+03FF・U+1F00–U+1FFF | `el-GR` | なし |
| `hebrew` | U+0590–U+05FF | `he-IL` | なし |
| `arabic` | U+0600–U+06FF・U+0750–U+077F・U+08A0–U+08FF | `ar-SA` | **あり**（fa/ur） |
| `devanagari` | U+0900–U+097F | `hi-IN` | **あり**（mr/ne） |
| `thai` | U+0E00–U+0E7F | `th-TH` | なし |
| `armenian` / `georgian` / `khmer` / `lao` / `myanmar` / `sinhala` / `amharic` / `bengali` / `tamil` / `telugu` / `kannada` / `malayalam` / `gujarati` / `gurmukhi` | それぞれの単一ブロック | 各言語 | なし |

⚠️ **句読点・記号・全角英数はどこにも入れない＝中立にする**。CJK 記号（U+3000–U+303F＝`、。「」`）も
**全角の約物**（U+FF01–U+FF65 の `，．！？`）も日中で共有するので、片方に寄せると発話が割れるうえ
**中国語の文が「かなを含む」と誤判定される**（下の「実装で踏んだ罠」＝当初この表のとおり
U+FF00–U+FFEF を丸ごと `kana` に入れて実際に壊した。**戻さないこと**）。

⚠️ **`LATIN_CHARS` と各範囲は交わらせない**（049 で踏んだ罠。テキスト全体に `test` をかける
判定があるため、重ねると文字単位の優先順位が効かずベトナム語が誤判定される）。

### 3. 漢字の曖昧さの解き方

読み上げる**面のテキスト**を見て推定する。

1. **かながあれば** → その面の `han` は**日本語**
2. **ハングルがあれば** → `han` は**韓国語**（漢字ハングル混じり）
3. どちらも無ければ → **設定値**

これで「表面『你好』／裏面『こんにちは、と言います』」の日中カードが自動で読み分かる
（裏はかなあり＝日本語、表はかな無し＝設定値＝中国語）。

⚠️ **推定なので外れる場合がある**。①純漢字の日本語（`非同期処理`）は、設定を中国語にしていると
中国語で読まれる ②1つの面に `你好 ＝ こんにちは` と両方書くと、かなが優先されて中国語部分も
日本語で読まれる。**これが Phase 2（デッキ単位の上書き）が事実上必要になる理由**で、
「中国語デッキだけ漢字＝中国語」にすれば①②とも解決する。

### 4. 短いラテン片の寄せ（049 の規則の一般化）

「3文字以下のラテン片は隣へ倒す」は**倒す先が日本語のときだけ**という現在の条件を維持する
（閾値3は日本語音声の実測値のため）。倒す先は「直前（無ければ直後）の区間の**解決後の言語**」。

### 5. 先頭の中立文字

現在は「先頭の中立文字（数字・記号）は非ラテン区間として始める」だが、
**次の区間へ吸わせる**に変える。049 で `1. GET` の `GET` が日本語側へ倒れるバグの原因だった
（今はガードで塞いでいるが、構造的に消したほうが良い）。中立しか無いテキストは `han` の言語で読む。

### 6. 設定画面

行が増えすぎないように2段構えにする。

```
言語設定                              ← 小見出し（「速度」と同じ階層）
  アルファベット ⓘ      English (en-US) >
  漢字 ⓘ                日本語 (ja-JP) >
  その他の文字体系 ⓘ                   >   ← 折りたたみ（キリル・アラビア・デーヴァナーガリー）
```

説明は各行の名前の右の ⓘ をタップして**下にインライン展開**する（同画面の目標・タイマーと同じ形。
`infoIcon`/`infoBox`）。⚠️ **ⓘ の Pressable は行の Pressable の内側に置く**＝内側が先にタッチを
取るのでピッカーは開かない。文言は `{{name}}部分を読み上げる言語を設定します。` の**1テンプレート**
で全文字体系を賄う（文字体系が増えても翻訳を足さなくてよい）。漢字だけ判別ルールを説明する別文言。

ハングル・タイ・ギリシャなどは**設定を出さない**（1対1なので選ばせる意味がない）。
さらに **端末が持っている音声が2つ未満の文字体系も出さない**（下記）。
ピッカーは既存の `SpeechLanguageModal` を `script: SpeechScript` に一般化し、
**選択肢はその文字体系を使う言語だけ**に絞る（漢字なら ja/zh/yue、キリルなら ru/uk/bg…）。

### 7. 言語の表示名は `locales` に持つ（`Intl.DisplayNames` は使えない）

一覧の項目は `English (en-AU)` のような「自称＋コード」ではなく、**UI 言語の表示名**
（日本語 UI なら `英語（オーストラリア）`）で出す。iOS の設定アプリと同じ見え方。

⚠️ **`Intl.DisplayNames` は使えない。** この iOS ビルドの Hermes（RN 0.81）は
`HERMES_ENABLE_INTL=true` でビルドされているが、`hermes.framework` の文字列を調べると
`DateTimeFormat` / `NumberFormat` / `Collator` はあるのに **`DisplayNames` は存在しない**。
したがって表示名は `locales/*.json` の `speechLang.*`（言語・約85件）と
`speechRegion.*`（地域・約65件）に持ち、`speechLanguageLabel(code, t)` が組み立てる。

⚠️ **表に無いコードはコードのまま返す**。選択肢は端末の音声一覧から作るので、OS が新しい
言語の音声を追加しても一覧には出続ける（ラベルが読めないだけで壊れない）＝
「対応表を持たない」という方針は**選択肢の一覧**についてのもので、表示名はその例外。

⚠️ 地域サブタグは `zh-Hans-CN` のような文字体系つきにも対応するため、
2文字（`US`）か3桁（`001`＝UN M49 の「世界」）に一致する部分を探して取る。

**`日本語（日本）` のような重複は許容する。** 「同じ言語が一覧に1つしか無ければ地域を出さない」
という抑制もできるが、設定画面の行は音声一覧の取得を待たずに描くので、
**読み込み後にラベルが変わってちらつく**。iOS の音声一覧も地域を併記するので許容とした。

### 8. ラテン文字の言語に「なし」（声を分けない）を置く

`HTML`（4文字）は英語の声で「エイチティーエムエル」、`CSS`（3文字）は短ラテン寄せで日本語の声で
「シーエスエス」——**どちらも読みとしては正しいのに、同じ文の中で読み分けが起きる**のが
分かりにくい、という指摘から追加した。ラテン文字の言語に `SPEECH_LANG_NONE`（`'none'`）を選ぶと、
ラテン文字の区間も**もう一方の声**で読むので切り替えが一切起きない。

⚠️ **漢字側の解決をそのまま使う**（`langForScript('han', …)` を呼ぶ）＝かな/ハングルの推定も
効くので、周りの日本語と同じ声になって1発話に畳まれる。既定へ落とすと、漢字を中国語にしている
人のラテン文字だけ中国語の声になり「分けない」目的から外れる。
⚠️ **ラテン文字にだけ出す**（漢字に「なし」＝漢字を英語の声で読む、は意味を成さない）。
⚠️ 端末の音声一覧には無い値なので**UI 側で先頭に足す**。BCP-47 に `none` は無いので衝突しない。

代償は英語の発音が得られないこと（`idempotent` が「イデンポテント」）。049 で「日本語の声だけで
混在文を読む」は許容できないと判断したが、**設定で選べるなら話が別**で、既定の挙動は変えずに
「日本語で滑らかに聞きたい人」の逃げ道になる。

### 9. 選択肢が2つ未満の文字体系は行を出さない

「1対1の文字体系は設定を出さない」を**端末の実態にも適用する**。多くの端末でアラビア文字の音声は
1つ（`ar-SA` か `ar-001`）・デーヴァナーガリーは `hi-IN` だけなので、行を出しても選べない。
判定は `getConfigurableScriptLanguages()`（**音声一覧を1回だけ取得**）の件数で行い、
設定画面のマウント時に読む。⚠️ 未取得のあいだは出す側に倒す（行が消えて見えるちらつき防止）。
「その他の文字体系」に出すものが0件なら、その行ごと出さない。

**アプリ側に「この文字体系は1つだけ」という表は持たない**＝OS やユーザーが音声を足せば
（設定 → アクセシビリティ → 読み上げコンテンツ → 声）コードを変えずに行が現れる。

### 10. 旧設定からの移行

`speechNonLatinLang`（049）は1つの値で非ラテン全体を指していたので、**その言語が使う文字体系の
設定へ移す**（`ja`→`han=ja`、`zh-CN`→`han=zh-CN`、`ru`→`cyrillic=ru`、`ko`/`th` などは
既定と同じなので何もしない）。hydrate 時に一度だけ変換し、以後は新キーだけを読む。

### Phase 3（声の選択）が必要な理由＝実機で分かった iOS の挙動

アプリは `Speech.speak(text, { language })` と**言語タグだけ**を渡していて、`expo-speech` は
それを `AVSpeechSynthesisVoice(language:)` に流す。実機で確かめたところ、この API は

> **設定で選ばれている声が、要求された言語タグに一致すればそれを返す。
> 一致しなければその言語の既定（＝最初の声）を返す。**

という動きだった（iOS 設定 → アクセシビリティ → 読み上げコンテンツ → 声 → 英語 で
オーストラリアの男性を選ぶとアプリもその声になり、アメリカの声を選ぶとアプリの `en-AU` は
豪州の既定＝女性に戻る）。**英語の声は設定で1つしか選べない**ので、

- 「アプリはオーストラリア英語の男性・システムの読み上げは別の英語」という組み合わせが作れない
- **強化版・プレミアム版の声はこの経路で選ばれないことがある**

という制約になる。`expo-speech` には `voice: identifier` を渡す口があり、
`getAvailableVoicesAsync()` は `identifier`・`name`・`quality` を返すので、**アプリ側で選べる**。

### Phase 3 の設計

**声は「文字体系ごと」ではなく「言語ごと」に持つ**（`speechVoices: Record<BCP-47, identifier>`）。

- 区間は**解決後の言語**で畳まれるので、声も言語で引くのが自然（かなと漢字が同じ `ja-JP` に
  解決されて1発話になったとき、文字体系キーだと「どちらの声か」が決まらない）
- 言語を変えても**前の言語の選択が残る**ので、戻したときに復元される（消す処理が要らない）

⚠️ **identifier は端末固有**（`com.apple.voice.compact.en-AU.Karen`）。iCloud 同期や JSON
エクスポートで別端末へ渡ると存在しないことがあり、**存在しない identifier を渡すと
`expo-speech` は例外を投げる**（`SpeechModule.swift` の `InvalidVoiceException`）。
そこで **`useSpeech` が起動時に端末の identifier 一覧を取り、実在するものだけを `speakText` に
渡す**（`filterKnownVoices`）。さらに `speak` を try/catch し、失敗したら**声なしで読み直す**
二重の保険を置く（ここを落とすと「同期した別端末で読み上げが無反応」になる）。

UI は各言語行の下に「声」の行を足し、**その言語の声が2つ以上あるときだけ**出す（Phase 1 の
「選択肢が2つ未満の行は出さない」と同じ規則）。一覧の先頭に **「自動」**（＝端末の既定に任せる）
を置く＝言語と違い、声は**選択を取り消せる必要がある**ため。

**各行の左端に試聴ボタン（▶）を置く**（選ぶまで声が分からないため）。行タップ＝選択／▶＝試聴で、
ⓘ と同じく**行の Pressable の内側**に置いて住み分ける。**左端**にするのは、声を比べるときに
連打するので名前の長さで位置が動かない固定列にしたいのと、右端を「選択状態（✓）」の場所として
分けたいため。⚠️ 試聴は**設定した速度**で鳴らす（実際の聞こえ方で判断できるように）／
⚠️ **モーダルを閉じたら必ず止める**。

**奇抜な声（ノベルティ音声）は一覧から外す。** `Bad News` や `Zarvox` に単語を読ませる場面は
学習アプリには無く、一覧が伸びるぶん邪魔になるだけ。⚠️ **判定は identifier の末尾トークン**で行う
（`NOVELTY_VOICE_TOKENS`）＝表示名は端末の言語で訳されることがあるが identifier は訳されない。
⚠️ **`com.apple.speech.synthesis.voice.*` を接頭辞ごと弾かないこと**＝同じ場所に `Alex` のような
まともな高品質音声も入っている。除外の結果その言語の声が1つ以下になれば「声」の行自体が消える
（Phase 1 の「選択肢が2つ未満は出さない」規則がそのまま効く）。

サンプル文は `VOICE_SAMPLE_TEXTS`（言語の接頭辞 → **その言語で書かれた文**）に持つ。
⚠️ **`locales` には置かない**＝UI 言語に翻訳するものではなく、声の言語で書かれていなければ
試聴の意味が無いため（タイ語の声に日本語を読ませても評価できない）。
⚠️ **表に無い言語は声の名前を読む**＝正しさを確信できない文を各国語で埋め込むより害が無い。
英語のサンプルに pangram を選んだのは、`lazy` の /eɪ/ でオーストラリア英語の母音を
確かめられるから（この機能の発端がその確認だった）。

⚠️ **既知の穴**：声の行は「表示されている言語行」にしか付かないので、漢字を中国語にしている
日本語話者は**かな（`ja-JP`）の声を選べない**（かなの行は1対1なので出していない）。
実害は「日本語の声が端末の既定になる」だけなので許容する。

### Phase 2（デッキ単位）の形

`decks.speechLangs` に `Record<SpeechScript, string>` の JSON 列を1つ足す（`htmlStages` と同じ
やり方＝`ALTER TABLE` で追加・空なら未設定）。解決順は **デッキ設定 → アプリ設定 → 文字体系の既定**。
学習画面はデッキを持っているので受け渡しは容易（`useSpeech` に渡す）。

⚠️ **上書きは「設定した文字体系だけ」**（丸ごと置き換えない）。中国語デッキで漢字だけ中国語に
したいときに、ラテン文字まで巻き込まれると英語の用語が中国語読みになる。

## 不採用（再提案しないこと）

### カード単位・面単位の言語設定

049 でも見送ったが、本チケットの Phase 1 でさらに不要になる。理由は3つ。

1. **Phase 1 でほとんど解決する**。面単位が要るのは「同じ文字体系なのに面ごとに言語が違う」
   場合だけ（表=英語／裏=スペイン語）。表=日本語／裏=英語 も 表=韓国語／裏=日本語 も自動で分かれる
2. **運用コストがユーザーに乗る**。1000枚のデッキに手作業で設定するのは現実的でなく、
   新規カードのたびに指定が要る＝「何も設定せずに読める」という本来の要求と逆向き
3. **1面の中の混在は解決しない**。`React の useEffect は副作用を扱う` のような最頻の形は
   面単位では扱えず、結局は文字体系の分割が要る

残る「同じ文字体系で言語が違う」場面は **デッキ単位（Phase 2）で埋める**。語学デッキは
1デッキ1言語がふつうなので、設定は1回で済む。

### 統計的な言語判定（n-gram 等）

049 と同じ理由で不採用。カードは短文で精度が出ず、同じデッキでカードごとに読み方が変わる。

### 簡体字テーブルによる日中の自動判別

`你`・`们`・`这`・`说` のような中国語専用字を持てば漢字の曖昧さを機械的に解けるが、
**表を持つコストと誤判定の説明しづらさ**に見合わない（デッキ単位の上書きのほうが予測可能）。
将来どうしても必要になったときの選択肢としてだけ記録する。

## 実装で踏んだ罠（Phase 1・2026-08-20）

### 全角の約物を `kana` に入れると中国語が日本語の声になる

当初 `kana` の範囲に全角形ブロック（U+FF00–U+FFEF）を丸ごと入れていた。ここには半角カナや
全角英数だけでなく**全角の読点・句点・感嘆符（`，．！？`）** も含まれる。これらは中国語でも
使うので、`你好，世界` の `，` が「かな」と判定され、

1. 漢字の区間が `，` で**割れる**（`你好` / `，` / `世界`）
2. **`hasScript(text, 'kana')` が真になり、漢字が日本語と推定される**（＝設定を中国語にしても
   日本語の声で読まれる）

の2つが同時に起きた。**句読点・記号は中立**（＝どこにも属さず隣へ吸われる）が正しい。
全角英数も同じ扱いにして隣へ吸わせる＝日本語文中なら日本語の声、中国語文中なら中国語の声になる
（`kana` に入れると中国語の文に全角英数があるだけで①②を再発させる）。`kana` に残したのは
**半角カナ（U+FF66–U+FF9F）だけ**で、ハングルの半角形（U+FFA0–U+FFDC）は `hangul` へ入れた。

### 行の出し分けを「保存されているか」で判断してはいけない

「選択肢が2つ未満の行は出さない」を入れたとき、逃げ道として
**「上書きが保存されていれば件数に関わらず出す」**という条件を足した（設定したのに
取り消せない状態を作らないため）。これが2つの不具合を生んだ。

1. 選択肢が1つしかない行（アラビア文字）を**タップして選んだだけで上書きが保存され、
   行が永久に居座る**。ピッカーに「既定に戻す」は無いので**解除する手段が無い**
2. 対策として「**既定と同じ値なら保存しない**」を入れたが、**これも効かなかった**。
   ここでの既定は `SCRIPT_DEFAULT_LANGS` に固定で書いた `ar-SA` で、
   **端末が実際に持っている音声のタグ（`ar-001` など）と一致するとは限らない**。
   一致しなければ「既定と違う」と判定されて保存され、行は消えないままになる

**結論：行の出し分けの材料は端末の音声一覧だけにする。** 保存内容と結びつけない。
隠れている行に上書きが残っていても、選べる音声が1つなら結果の声は同じなので害はない。
⚠️ **`SCRIPT_DEFAULT_LANGS` の値は「その文字体系を読むならこの言語」という指定であって、
端末に存在する音声タグではない**（`Speech.speak` は近い声へ倒してくれる）。
**この2つを等値で比較するロジックを書かないこと。**

### 範囲表は `\uXXXX` エスケープで書く

当初は既存コードに合わせて実文字（`぀-ヿ` など）で書いたが、アラビア文字・ヘブライ文字の
範囲は**エディタ上で RTL 表示になり読めない**うえ、見た目が同じで別のコードポイントという
事故が起きうる。全部エスケープに統一し、**`SCRIPT_RANGES` の端点を実際に出力して**
意図した Unicode ブロック境界か確認した（`docs/050` 作業時のワンライナー）。
