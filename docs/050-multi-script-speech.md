# 050 読み上げの多言語対応（文字体系 → 言語の解決表）

**フェーズ:** 将来
**ステータス:** **未着手**（設計合意 2026-08-20）
**要ネイティブ再ビルド:** 不要（`expo-speech`・`expo-localization` とも導入済み）
**依存:** 049（読み上げ本体）
**被依存:** なし

---

## 概要

読み上げの言語決定を「ラテン文字／それ以外」の**2バケツ**から、**文字体系ごとの解決表**へ広げる。

```
現在（049）  ラテン文字 → 設定の言語 ／ それ以外 → 設定の言語（1つ）
本チケット   ラテン文字 → 設定 ／ かな → 日本語 ／ ハングル → 韓国語 ／ タイ文字 → タイ語 …
             漢字 → 設定（日本語 or 中国語）／ キリル → 設定（既定ロシア語）…
```

狙いは **日本語と韓国語・中国語・ロシア語などが混ざるカードを、設定なしで読み分けること**。
語学学習で使うと現状は「日本語と英語」しか読み分けられず、韓国語カードも日本語の声で読まれる。

---

## なぜできるのか（前提の訂正）

049 では「分けられるのは文字体系であって言語ではない」と書き、そこから
「**設定は1つ**（ラテン文字を何語で読むか）」を導いた。この推論は**片側が誤り**だった。

文字体系で分けられないのは「**同じ文字を共有する言語同士**」だけで、
**日本語と韓国語・タイ語・ロシア語・ギリシャ語などは文字体系そのものが違う＝原理的に分けられる**。

| 組み合わせ | 自動判別 | 理由 |
|---|---|---|
| 日本語 ⇔ 韓国語 | **○** | ハングルは韓国語しか使わない |
| 日本語 ⇔ ロシア語 / タイ語 / ギリシャ語 / アラビア語 / ヒンディー語 | **○** | いずれも固有の文字体系 |
| 日本語 ⇔ 英語・スペイン語… | **○** | かな漢字 vs ラテン文字（049 で実装済み） |
| **日本語 ⇔ 中国語** | **△** | 漢字は同じコードポイント。**かなの有無**で推定はできる |
| 英語 ⇔ スペイン語 ⇔ ベトナム語 | **✗** | 同じラテン文字。**原理的に不可能** |

つまり ✗ は2つだけ（ラテン文字の中／漢字の中）で、そこにだけ設定を置けばよい。
049 が日韓を分けられないのは Unicode の制約ではなく、**非ラテンを1バケツに畳んだ実装の都合**。

## 確定仕様（設計合意・2026-08-20）

| 論点 | 決定 |
|---|---|
| 解決の単位 | **文字体系**（`SpeechScript`）→ 言語（BCP-47） |
| 設定を置く範囲 | **曖昧な文字体系だけ**（ラテン・漢字・キリル・アラビア・デーヴァナーガリー）。1対1のものは設定を出さない |
| 既定値 | 1対1の文字体系はその言語。曖昧なものは端末言語から（日本語端末なら漢字＝日本語） |
| 粒度 | Phase 1 = アプリ設定 → Phase 2 = **デッキ単位の上書き** → カード/面単位は**やらない**（下記） |
| 漢字の曖昧さ | **かな/ハングルが同じ面にあれば日本語/韓国語**、無ければ設定値（推定であって確定ではない） |
| 発話の分割 | **細かく割ってから、同じ言語に解決された隣接区間を畳む**（下記） |
| Pro ゲート | なし（049 と同じく無料機能） |

## 設計

### 1. 細かく割ってから、言語で畳む

素直に文字体系で割ると**日本語の文が漢字とかなで細切れになり**、発話境界だらけで間延びする
（`Speech.speak()` は1発話ごとに間が入る）。順序を分けることで解決する。

```
splitByScript(text)        文字体系で細かく割る（kana / han / latin / hangul …）
  ↓
resolveLangs(runs, langs)  各区間を言語へ解決する（han の推定はここ）
  ↓
mergeByLang(runs)          隣り合う同じ言語の区間を畳む  ← 日本語は漢字＋かなで1発話に戻る
  ↓
speakText                  区間ごとに声を変えてキューへ積む
```

⚠️ **畳むのは「文字体系が同じ」ではなく「解決後の言語が同じ」区間**。ここを間違えると
日本語が細切れのままになるか、漢字＝中国語の設定時に日本語と中国語が1発話に混ざる。

### 2. 文字体系の一覧（範囲表）

`lib/speech.ts` に `SCRIPT_RANGES` を持つ。現在の `RE_NON_LATIN` を分解して名前を付けるだけ。

| script | 主な範囲 | 既定の言語 | 設定 |
|---|---|---|---|
| `latin` | 現在の `LATIN_CHARS`（ASCII＋U+00C0–U+024F＋U+1E00–U+1EFF） | `en-US` | **あり**（既存） |
| `kana` | U+3040–U+30FF・U+31F0–U+31FF・U+FF00–U+FFEF（全角英数・半角カナ） | `ja-JP` | なし |
| `han` | U+3400–U+4DBF・U+4E00–U+9FFF・U+F900–U+FAFF | 端末言語（`zh`/`ko` なら該当、他は `ja-JP`） | **あり** |
| `hangul` | U+1100–U+11FF・U+3130–U+318F・U+A960–U+A97F・U+AC00–U+D7FF | `ko-KR` | なし |
| `cyrillic` | U+0400–U+052F・U+1C80–U+1C8F | `ru-RU` | **あり**（uk/bg/sr/mk/be） |
| `greek` | U+0370–U+03FF・U+1F00–U+1FFF | `el-GR` | なし |
| `hebrew` | U+0590–U+05FF | `he-IL` | なし |
| `arabic` | U+0600–U+06FF・U+0750–U+077F・U+08A0–U+08FF | `ar-SA` | **あり**（fa/ur） |
| `devanagari` | U+0900–U+097F | `hi-IN` | **あり**（mr/ne） |
| `thai` | U+0E00–U+0E7F | `th-TH` | なし |
| `armenian` / `georgian` / `khmer` / `lao` / `myanmar` / `sinhala` / `amharic` / `bengali` / `tamil` / `telugu` / `kannada` / `malayalam` / `gujarati` / `gurmukhi` | それぞれの単一ブロック | 各言語 | なし |

⚠️ **`kana` に全角形（U+FF00–U+FFEF）を含める**のは、全角英数・半角カナが日本語の文脈でしか
出ないため。⚠️ **CJK 記号（U+3000–U+303F＝`、。「」`）は中立にする**（日中で共有するため、
どちらかに寄せると隣の区間から切り離されて発話が割れる）。

⚠️ **`LATIN_CHARS` と各範囲は交わらせない**（049 で踏んだ罠。テキスト全体に `test` をかける
判定があるため、重ねると文字単位の優先順位が効かずベトナム語が誤判定される）。

### 3. 漢字の曖昧さの解き方

読み上げる**面のテキスト**を見て推定する。

1. **かながあれば** → その面の `han` は**日本語**
2. **ハングルがあれば** → `han` は**韓国語**（漢字ハングル混じり）
3. どちらも無ければ → **設定値**

これで「表面『你好』／裏面『こんにちは、と言います』」の日中カードが自動で読み分かる
（裏はかなあり＝日本語、表はかな無し＝設定値＝中国語）。

⚠️ **推定なので外れる場合がある**。①純漢字の日本語（`非同期処理`）は、設定を中国語にしていると
中国語で読まれる ②1つの面に `你好 ＝ こんにちは` と両方書くと、かなが優先されて中国語部分も
日本語で読まれる。**これが Phase 2（デッキ単位の上書き）が事実上必要になる理由**で、
「中国語デッキだけ漢字＝中国語」にすれば①②とも解決する。

### 4. 短いラテン片の寄せ（049 の規則の一般化）

「3文字以下のラテン片は隣へ倒す」は**倒す先が日本語のときだけ**という現在の条件を維持する
（閾値3は日本語音声の実測値のため）。倒す先は「直前（無ければ直後）の区間の**解決後の言語**」。

### 5. 先頭の中立文字

現在は「先頭の中立文字（数字・記号）は非ラテン区間として始める」だが、
**次の区間へ吸わせる**に変える。049 で `1. GET` の `GET` が日本語側へ倒れるバグの原因だった
（今はガードで塞いでいるが、構造的に消したほうが良い）。中立しか無いテキストは `han` の言語で読む。

### 6. 設定画面

行が増えすぎないように2段構えにする。

```
アルファベットの言語   English (en-US)        ← 既存
漢字の言語             日本語 (ja-JP)         ← 新規
その他の文字体系        自動 >                ← 折りたたみ（キリル・アラビア・デーヴァナーガリー）
```

ハングル・タイ・ギリシャなどは**設定を出さない**（1対1なので選ばせる意味がない）。
ピッカーは既存の `SpeechLanguageModal` を `kind: SpeechScript` に一般化し、
**選択肢はその文字体系を使う言語だけ**に絞る（漢字なら ja/zh/yue、キリルなら ru/uk/bg…）。

### 7. 旧設定からの移行

`speechNonLatinLang`（049）は1つの値で非ラテン全体を指していたので、**その言語が使う文字体系の
設定へ移す**（`ja`→`han=ja`、`zh-CN`→`han=zh-CN`、`ru`→`cyrillic=ru`、`ko`/`th` などは
既定と同じなので何もしない）。hydrate 時に一度だけ変換し、以後は新キーだけを読む。

したいときに、ラテン文字まで巻き込まれると英語の用語が中国語読みになる。

## 不採用（再提案しないこと）

### カード単位・面単位の言語設定

049 でも見送ったが、本チケットの Phase 1 でさらに不要になる。理由は3つ。

1. **Phase 1 でほとんど解決する**。面単位が要るのは「同じ文字体系なのに面ごとに言語が違う」
   場合だけ（表=英語／裏=スペイン語）。表=日本語／裏=英語 も 表=韓国語／裏=日本語 も自動で分かれる
2. **運用コストがユーザーに乗る**。1000枚のデッキに手作業で設定するのは現実的でなく、
   新規カードのたびに指定が要る＝「何も設定せずに読める」という本来の要求と逆向き
3. **1面の中の混在は解決しない**。`React の useEffect は副作用を扱う` のような最頻の形は
   面単位では扱えず、結局は文字体系の分割が要る

残る「同じ文字体系で言語が違う」場面は **デッキ単位（Phase 2）で埋める**。語学デッキは
1デッキ1言語がふつうなので、設定は1回で済む。

### 統計的な言語判定（n-gram 等）

049 と同じ理由で不採用。カードは短文で精度が出ず、同じデッキでカードごとに読み方が変わる。

### 簡体字テーブルによる日中の自動判別

`你`・`们`・`这`・`说` のような中国語専用字を持てば漢字の曖昧さを機械的に解けるが、
**表を持つコストと誤判定の説明しづらさ**に見合わない（デッキ単位の上書きのほうが予測可能）。
将来どうしても必要になったときの選択肢としてだけ記録する。

## 実装メモ（着手時に読む）

- 分割・解決・畳み込みはすべて `lib/speech.ts` に閉じる。`blocksToSpeech.ts`（テキスト生成）と
  `useSpeech.ts`（再生状態）は**触らない**か、設定を渡す1行だけ変える
- `getSpeechLanguages(script)` は「その文字体系を使う言語」の接頭辞表で絞る。
  049 の `NON_LATIN_SCRIPT_PREFIXES` はこの表に吸収される
- テキスト処理を触るので `npm run verify:speech` を必ず流す（現在 59 アサーション）
- 端末に音声が無い言語は無音や別の声になる。ピッカーは `getAvailableVoicesAsync()` の
  結果だけを出す現在の方式を維持する（対応表をアプリに持たない）
